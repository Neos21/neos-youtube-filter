# Documentation Rules

Markdown とドキュメンテーションコメントを変更する場合に適用する。


## 情報の配置

- `README.md` は概要、開始方法、主要機能、文書索引を扱う
- Architecture (`ARCHITECTURE.md`) はシステム構成、依存方向、レイヤー責務を扱う
- Domain はビジネスルールを扱う
- Feature 文書は利用者から見える現行仕様を扱う
- API 文書はエンドポイントと共通契約を扱う
- ADR (`docs/decisions/`) は選択理由と却下案を将来参照する必要がある判断だけを扱う
- Maintenance は依存関係やツールに関する開発者向け保守メモを扱う
- `docs/README.md` と各サブディレクトリの `README.md` は、文書の配置方針と索引を扱う
- 同じ説明を複数文書に複製せず、詳細を所有する文書にリンクする


## Markdown とコードコメントの境界

- 画面・API・データの現行仕様は Markdown に記載する
- 特定の型・関数・SQL に閉じた実装意図はコードコメントに記載する
- 実装前のタスク分割、完了済み変更一覧、一時的な検証チェックリストは現行仕様文書に残さない
- Markdown を削除する前に、恒久的な仕様と設計意図が別文書またはコードコメントに移行済みか確認する


## ドキュメンテーションコメント

- 関数、型、主要オブジェクトとそのプロパティには、役割や値の意味が型・名前だけで分からない場合にコメントを書く
- 複数行のドキュメンテーションコメントで段落を区切る空行は ` * ` とし、アスタリスクの直後に半角スペースを1つ残して垂直位置を揃える
- `null` の条件、処理順、ソート優先順位、Map による集約理由などの実装意図を優先する
- Boolean 値を説明する場合は「～か否か」と記述して `true` が表す状態を明確にし、「～かどうか」は使用しない
- 名前と型を言い換えるだけのコメントや、型から明らかな `@param`・`@returns` を追加しない
- 定数・Schema・仕様文書で管理する変更可能な値域や件数をコメントに重複記載せず、コメントでは値の意味と参照関係を説明する
- 関連する型・関数・定数を参照すると理解しやすい場合は `@see {@link XXX}` を使う
- 対象を指す助詞は「～へ」より「～に」を優先し、何に対する説明かを正確にする
- 用語、助詞、句読点は既存コメントと比較し、同じ概念に同じ表現を使う


## 既存コメント

- 既存コメントを削除・変更する場合は事前に開発者に確認を取る
- 実装上不要になった場合も、必要であれば「なぜ現在の実装になっているか」を説明するコメントに置き換える
- 対象外のコメントや空白を整形しない
