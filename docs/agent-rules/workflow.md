# Workflow Rules

ワークフローのルール。


## 実装単位

- `TASKS.md` が存在する場合は、先頭の未完タスクを確認する
- 変更範囲を1回でレビュー可能な大きさに分ける
- 1タスクごとに実装し、開発者のレビューを受ける
- 実装前に変更方針と対象ファイルを確認する
- 開発者が全コードをレビューできるよう、変更量が大きい場合は事前にタスクを分解する
- 大きな変更や TODO 実装では、責務、対象ファイル、API、UI State、検証方法を整理して開始確認を取る
- 開発者が承認した範囲を超えて、関連しそうな別修正に拡大しない
- ユニットテストの実装は開発者から明示的に指示した場合のみ実装し、通常は実装対象外とする


## 既存変更の保護

- 作業開始前と完了前に `$ git status --short` を確認する
- 既存のステージ済み・未ステージ変更を保持する
- 対象外ファイルの生成差分や整形差分を混入させない
- ビルドで `worker-configuration.d.ts` などが変化した場合は、今回の設定変更に必要な差分か確認する


## 検証

- 意味のある変更では `$ git diff --check`、`$ npm run lint`、`$ npm run build` を実行する
- Lint が自動修正を行うため、実行後に差分を再確認する
- 3回以上の修正・再検証でもエラーが残る場合は処理を中止する
- コマンド自体を実行できない場合も処理を中止し、実行できなかった内容を報告する


## 報告

- 完了した変更をファイル単位ではなく、利用者・保守者にとっての結果として説明する
- 実行した検証と成否を報告する
- 既存変更との重なり、未解決事項、次タスクに進むための条件があれば明記する
